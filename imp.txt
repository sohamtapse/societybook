============================================================ 1. PRODUCT
OVERVIEW ============================================================

Build a multi-tenant Society Management and Complete Accounting SaaS for
cooperative housing societies.

Technology stack: - Next.js App Router - TypeScript - Tailwind CSS -
shadcn/ui - Neon PostgreSQL - Drizzle ORM - JWT-based authentication -
Zod validation - decimal.js for exact monetary calculations - Recharts
for dashboards - S3-compatible object storage for documents, payment
proofs and QR images - Server-side authorization and database access
only

The application has three separate portals:

1.  Platform Super Admin portal (the SaaS owner/operator).
2.  Society Admin and staff portal.
3.  Resident portal.

The platform supports multiple societies in one shared Neon PostgreSQL
database. Society A must never be able to access Society B’s records.

Every society-owned record must be tenant-scoped and protected by
server-side authorization, composite database constraints and, where
practical, PostgreSQL Row-Level Security (RLS).

The system must have a real double-entry accounting engine. Posted
journal lines are the financial source of truth. Do not build this as a
simple maintenance collection CRUD application.

============================================================ 2. BUSINESS
MODEL AND PAYMENT SEPARATION
============================================================

There are TWO completely separate payment flows.

A. SaaS subscription payments: - Society Admin/customer pays the SaaS
provider. - Use the platform payment gateway ONLY for SaaS subscription
fees. - Support monthly/annual plans, subscription invoices, renewals,
expiry, webhook verification, failed payments and subscription status. -
Platform Super Admin creates societies, assigns plans and controls
limits. - Platform Super Admin allocates a maximum number of flats to
each society. - Enforce flat limits in backend/database transactions,
not only in the UI. - Subscription revenue belongs to the SaaS platform.

B. Society payments: - Residents pay the society directly. - Each
Society Admin configures the society’s own UPI ID, QR code and/or bank
details. - Residents scan the society’s QR and pay directly to the
society’s bank/UPI account. - The SaaS platform must not collect, pool
or route society maintenance payments into the SaaS provider’s merchant
account. - Resident can submit UTR/reference number and optionally
payment proof. - Payment submission creates a PENDING verification
record. It must not automatically mark dues paid. - Authorized society
staff verifies the payment against bank/UPI records and approves or
rejects it. - After approval, create the receipt and post the accounting
journal entry. - A static UPI QR does not independently confirm payment.
Automatic confirmation requires a supported bank/UPI verification
integration; otherwise use manual UTR verification and approval. - Cash
and bank transfer payments must also be supported.

Keep separate tables/modules for subscription payments and society
payments.

Suggested platform tables: - platform_users - platform_roles -
societies - plans - subscriptions - subscription_invoices -
subscription_payments - subscription_webhooks - society_limits -
platform_audit_logs

Suggested society payment tables: - society_payment_methods - payments -
payment_verifications - payment_allocations - receipts

============================================================ 4. RESIDENT
ACCOUNT / FLAT LOGIN REQUIREMENTS
============================================================

Initial product approach: - Start with one resident portal login account
per flat. - Design the database so individual owner/tenant logins can be
added later without redesigning the whole system. - A flat may have
multiple owners and tenants in its occupancy history. The initial shared
flat login is a portal access account, not a replacement for
resident/occupancy records.

When Society Admin creates/allocates a flat: - Backend automatically
generates a unique flat username. - Example: society code GREENVALLEY +
flat A-101 => GREENVALLEY-A101. - Username generation must normalize
characters and handle collisions. - Enforce unique constraint for
username within the chosen login namespace. If login is globally
username-based, ensure globally unique usernames; alternatively require
society code as part of username. - Generate a cryptographically random
temporary password using a secure random generator. - Store only an
Argon2id password hash. Never store plaintext or reversibly encrypted
passwords. - Display the generated initial password to the admin only
once, immediately after provisioning, so the admin can copy/share it. -
Do not provide a way to view/retrieve an existing password. Password
hashing is intentionally one-way. - Society Admin can reset a
resident/flat password at any time. - On reset, generate a new random
password, hash it, invalidate the old password, revoke all active
sessions for that account, increment credential version and display the
new password to the admin once. - Admin can view usernames and account
status, but not existing passwords. - Admin can disable/reactivate
resident portal accounts. - Resident cannot change their own password.
Password changes are admin-initiated resets only. - Record all
provisioning, reset, disable and reactivation events in the audit log. -
Only authorized admin/staff permissions can reset credentials.

IMPORTANT SECURITY REQUIREMENT: The user requested that the Society
Admin be able to see existing passwords. Do NOT implement this
literally. It is unsafe to store retrievable passwords. Implement the
secure equivalent: admin can reset the password and view/copy the newly
generated password once. Admin cannot view an existing password. Explain
this security constraint in the product documentation and admin UI.

Suggested flat_portal_accounts fields: - id - society_id - flat_id -
username - password_hash - status - credential_version -
password_changed_at - created_at - last_login_at

Suggested related tables: - resident_sessions - credential_reset_logs -
login_attempts

============================================================ 5.
AUTHENTICATION AND SECURITY
============================================================

Use JWT-based authentication with: - Short-lived access JWT (e.g. 10-15
minutes). - Refresh tokens with rotation and revocation (e.g. 7-30 days,
configurable). - HTTP-only, Secure, SameSite cookies. - Never store
access or refresh tokens in localStorage. - Password hashing with
Argon2id. - Rate limiting and lockout/backoff for repeated login
failures. - Secure logout and session revocation. - Validate account
status and current session on sensitive operations. - CSRF protections
appropriate to cookie-based authentication. - Zod for input
validation. - Never trust society_id, flat_id, role or permissions sent
by the browser. - Derive tenant and identity from verified session/JWT,
then validate membership and entity ownership on the server. - JWT
claims may include sub, accountType, societyId, flatId (resident only),
sessionId and credentialVersion. - Do not rely on JWT claims alone for
sensitive authorization; validate active account/session and current
permissions. - Separate admin/staff and resident authorization
policies. - Do not expose database credentials to browser code. - Keep
secrets in environment variables. - Refresh token should be stored
hashed in the database. - Revoke all refresh sessions for a resident
account on password reset. - Log security-relevant events without
logging passwords or tokens.

============================================================ 6.
MULTI-TENANT DATABASE ARCHITECTURE
============================================================

Use one shared Neon PostgreSQL database initially, with society_id on
every society-owned table.

Mandatory isolation controls: - Every society-owned table must contain
society_id (or be related through a strictly enforced tenant-owned
parent). - Use composite unique constraints such as (society_id, id). -
Use composite foreign keys such as (society_id, flat_id) referencing
(society_id, id), so a Society A payment cannot reference a Society B
flat. - Add indexes beginning with society_id for tenant-scoped access
patterns. - Consider PostgreSQL Row-Level Security (RLS) as defense in
depth. - Set tenant context transaction-locally for RLS and never use a
persistent connection-level tenant setting that can leak between pooled
requests. - Test cross-tenant access attempts explicitly. - Never rely
only on frontend filtering. - Use database transactions for multi-table
financial operations. - Do not create one Neon database per society for
the initial product.

SUBLEDGER DIMENSIONS ON JOURNAL LINES (flat-wise, vendor-wise,
fund-wise tracking)

A single control account such as Maintenance Receivable or Sundry
Creditors cannot by itself show who owes what. Do NOT solve this with a
separate balance table that becomes a second source of truth. Instead,
journal_lines must carry optional dimension columns so that flat-wise
dues, vendor ledgers and fund statements are all derived from posted
journal lines:

- flat_id (nullable): the flat the line relates to.
- vendor_id (nullable): the vendor/creditor the line relates to.
- fund_id (nullable): the society fund the line relates to.
- Optional later: resident_id/member_id, demand_id, bill_id and
  payment_id references for drill-down, or a generic party_type +
  party_id pair if more party types are needed.

Rules:
1. Dimension columns are tenant-scoped. Use composite foreign keys such
   as (society_id, flat_id) -> flats(society_id, id), (society_id,
   vendor_id) -> vendors(society_id, id) and (society_id, fund_id) ->
   society_funds(society_id, id), so a line can never point at another
   society's flat, vendor or fund.
2. Mark accounts in chart_of_accounts as subledger control accounts
   (for example requires_flat, requires_vendor, requires_fund flags).
   The posting service and a database check/trigger must reject a line
   on a flagged account that has no matching dimension. Example: a line
   on Maintenance Receivable must have flat_id; a line on Sundry
   Creditors must have vendor_id; a line on a fund account must have
   fund_id.
3. Dimensions are set at posting time by the central posting service
   from the source record: maintenance demand lines carry the flat_id;
   payment receipt and allocation lines carry the flat_id; bill and
   vendor payment lines carry the vendor_id; fund contribution,
   utilization and transfer lines carry the fund_id.
4. Advance payments and unallocated payments (credit balances of a flat)
   must also carry flat_id, on their own liability/control account, so
   the flat's net position (dues minus advances) is derivable.
5. Dimension values on posted lines are immutable like every other
   posted field. Corrections are made through reversal/correction
   entries that carry the same dimensions.
6. Add indexes beginning with society_id, such as (society_id, flat_id,
   account_id, entry_date) and (society_id, vendor_id, account_id,
   entry_date), (society_id, fund_id, account_id, entry_date), to keep
   subledger queries fast.
7. Reconciliation invariant: for every control account and period, the
   sum of its dimension-wise balances must equal the control account's
   general-ledger balance. Add an automated check and a report that
   flags any difference.
8. Any cached or materialized summary (for example flat outstanding for
   the dashboard) must be rebuildable from journal lines and
   reconciled against them, as required below.

Reports that rely on dimensions: flat-wise outstanding and flat ledger,
vendor ledger and payables ageing, fund-wise statement, and receivables
schedule for audit.

Mandatory accounting rules: - Every posted journal entry must have equal
debit and credit totals. - Each entry must belong to one society and one
financial year/accounting period. - Debit and credit must be
non-negative and a line must not have both debit and credit greater than
zero. - Posted entries must be immutable. - Corrections must use
reversal/correction entries, never deletion or silent editing. - Every
journal entry must have source_type/source_id (maintenance demand,
payment, expense, manual journal, fund transaction, etc.). - Prevent
posting into locked accounting periods. - Journal header and lines must
be created atomically in one database transaction. - Posting service
must validate balanced totals using exact decimal arithmetic. - Use
PostgreSQL NUMERIC(14,2) or suitable precision for money; do not use
JavaScript floating-point for money. - Use exact decimal arithmetic in
application services. - Add database constraints and, where appropriate,
triggers/controlled procedures as additional safeguards. - Voucher
numbering must be unique within the relevant society/financial
year/series. - Add maker-checker approval for sensitive transactions if
enabled by society policy. - Maintain full audit history. - Implement
idempotency keys/source uniqueness to prevent duplicate posting from
retries/webhooks. - Do not update cached balances independently. If
materialized summaries/caches are added for performance, they must be
rebuildable and reconciled against journal lines.

Reports derived from posted journal lines: - Cash book - Bank book -
Journal register - General ledger - Trial balance - Balance sheet -
Income and expenditure statement - Receivables/payables - Fund-wise
balances - Flat-wise ledger and outstanding (by flat_id) - Vendor ledger
(by vendor_id) - Audit schedules

============================================================ 9. BANK
RECONCILIATION - NO BANK CONNECTION REQUIRED FOR MVP
============================================================

Bank reconciliation means comparing the society’s bank statement with
the bank transactions recorded in the application’s accounting ledger.

A direct bank account connection is NOT required for the initial
version.

MVP workflow: 1. Society Admin downloads a statement from their bank. 2.
Admin uploads CSV or Excel statement. 3. Application parses and
validates statement rows. 4. Application attempts to match bank
transactions with posted ledger transactions using date, amount,
UTR/reference and description. 5. Show matched, unmatched and ambiguous
transactions. 6. Admin reviews and confirms matches. 7. Missing bank
charges or other transactions can be entered through an authorized
accounting workflow. 8. Generate a reconciliation report showing book
balance, bank statement balance and reconciling items. 9. Preserve the
imported statement and reconciliation audit trail.

Do not automatically create accounting entries just because a statement
row is imported. Require review/approval for unmatched entries and
adjustments.

Possible future enhancement: - Authorized bank-data provider or
supported bank API integration, only after evaluating availability,
cost, consent, security and compliance. - Never request or store
internet banking passwords.

============================================================ 18.
IMPORTANT BUSINESS AND SECURITY RULES
============================================================

1.  A resident payment is not confirmed merely because the resident
    uploads a screenshot or UTR. It must be verified by authorized
    society staff or a trusted payment verification integration.
2.  A receipt should only be issued according to the society’s
    configured receipt policy after payment confirmation.
3.  Never delete posted journal entries.
4.  Never edit posted journal lines silently.
5.  Use reversal/correction entries.
6.  Never store plaintext passwords.
7.  Admin can reset resident passwords and see the newly generated
    password once, but cannot view an existing password.
8.  Residents cannot change their own password.
9.  Every sensitive action must be audited.
10. Never trust society_id from the client.
11. Every tenant-owned query must be tenant-scoped.
12. Use database constraints to prevent cross-tenant references.
13. Use exact decimal arithmetic for money.
14. Do not treat unverified payments as collections.
15. Do not mix SaaS subscription revenue with society funds.
16. Do not claim statutory compliance until reviewed by a qualified
    professional.
17. Do not store internet banking passwords or ask users to provide
    them.
18. Do not automatically create journal entries from imported bank
    statement rows without review.
19. Do not let cached balances become an independent source of truth.
20. Make financial operations idempotent and transactional.
